# DPDMS databases

Design decision: **one MySQL schema per service** (the "database-per-service"
pattern). No service reads another's tables — they talk over HTTP only. That is
what makes every service independently deployable and lets each member own their
own data end-to-end. Schemas are auto-created by
`?createDatabaseIfNotExist=true` (local dev) and by `db/init/01-create-databases.sql` (Docker).
Tables themselves are generated by Hibernate (`ddl-auto=update`).

## Overview (7 schemas, 8 tables)

| Schema | Service (owner) | Tables |
|--------|-----------------|--------|
| dpdms_auth | auth-service (Sean) | `user_accounts` |
| dpdms_flood | flood-service (Tanaka) | `flood_incidents` |
| dpdms_drought | drought-service (Oliver) | `drought_incidents` |
| dpdms_fire | fire-service (Sean) | `fire_incidents` |
| dpdms_zoonotic | zoonotic-disease-service (Rejoice) | `zoonotic_incidents` |
| dpdms_mining | mining-accident-service (Todzani) | `mining_accidents` |
| dpdms_alert | alert-service (Todzani) | `alert_logs` |

report-service and dashboard-service keep **no** database — they always fetch
live data from the hazard services, so a report can never be stale.

## 1. `dpdms_auth.user_accounts` (Sean)

| Column | Type | Rules | Meaning |
|--------|------|-------|---------|
| id | BIGINT | PK, auto-increment | surrogate key |

## 2. Shared shape of every incident table (flood / drought / fire / zoonotic / mining)

Every hazard table starts and ends the same way — only the indicator columns
in the middle differ. This deliberate repetition is what keeps the five services
independent (no shared library / shared DB that could couple them).

## ER diagrams

Rendered images live in `docs/diagrams/`:
- `er-diagram.png` — the full set (one entity box per service schema, with the
  logical "via HTTP" links the gateway creates between them).

There are deliberately **no foreign keys between schemas**: the only cross-service
"relationship" is the gateway forwarding identity headers, and alert-service
storing a logical `incident_id` (no FK — the incident lives in another database).
If the teacher asks: that is the standard microservices trade-off — we chose
independent deployability over cross-database joins.
